# Patrol Radar Pro — Open Testing release gate

Android package: io.github.missionaryj.patrolradar. Subscription product: patrol_radar_pro, base plan: monthly, U.S. price: $1.99/month. **Open Testing only. Never production.**

## Code delivered
- Native Google Play Billing Library 9.1.0 product lookup, monthly purchase, restore and pending-state callbacks.
- Supabase-authenticated server calling Google's purchases.subscriptionsv2.get API before unlocking Pro. Server stores purchase tokens privately with RLS, acknowledges after fulfillment, and applies expiry and state policy.
- Google Cloud Pub/Sub real-time developer notifications (RTDN), with authenticated OIDC push and Google re-verification, for renewals, cancellations and refunds.
- Effective Pro on Android = install-date founder (firstInstallTime before 2026-11-16T19:54:00-06:00, persisted as pr.foundingTester) OR server-verified Pro OR, while the verifier is unreachable, the last server-verified status cached on the device (founder: permanent; Play: until Google expiry + 3 days). Founders keep every Pro feature offline and when Supabase is down. The web build never grants Pro (src/entitlement/proAccess.ts).
- Automatic founder migration: on launch the app posts its install time and checkout account hash to `founder-install`; the server records a permanent pro_founders grant (source install_date) and can recover it after a reinstall on the same phone (source device_recovery). The single-use code box stays as a fallback for new phones.
- Reinstall recovery for subscribers: checkout sets `setObfuscatedAccountId` to SHA-256 of a salt + the per-app ANDROID_ID. When a token is already owned by another anonymous user, the server moves it to the caller only if Google's `externalAccountIdentifiers.obfuscatedExternalAccountId` equals the hash the caller presents (`relink_pro_purchase`, compare-and-set). Otherwise the app shows a clear "linked to a different install" message (HTTP 409).
- Billing uses its own auth session (`pr.pro.auth`), separate from City Chat (`pr.chat.auth`).
- Free Stop History preview; verified users get full shading and filters. Web has no Play checkout.

## Backend and Google Cloud setup (required before merging)
1. Apply the three Supabase migrations in order: 20261117000000_play_pro_entitlements.sql, 20261118000000_pro_purchase_owner_immutable.sql, 20261119000000_pro_founder_auto_claim_and_relink.sql (`supabase db push`, or paste each into the SQL editor). Inspect RLS, the service-role-only RPCs (claim_pro_founder_code, claim_pro_founder_install, relink_pro_purchase), the ownership trigger, and the ON DELETE RESTRICT foreign keys. Behavior checks: `scripts/test-pro-migrations.sh` (throwaway local Postgres; needs initdb) runs `scripts/pro-migrations-check.sql`.
   - ON DELETE RESTRICT (was CASCADE): deleting an auth user must never silently erase a paid purchase record or a permanent founder grant. Anonymous-user cleanup jobs will fail for those users until an operator handles the entitlement deliberately. SET NULL was rejected because user_id is NOT NULL by design and the ownership trigger blocks owner changes.
2. Enable Google Play Android Developer API in the Play-linked Google Cloud project. Create a narrowly privileged service account and authorize Play Console API access to view purchase status and acknowledge subscriptions.
3. Set Supabase Edge Function secret GOOGLE_PLAY_SERVICE_ACCOUNT_JSON to the complete JSON service account credential via secure Supabase secrets; do not commit keys, store them in Android, or paste them into chat. Ensure SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY are available to server functions.
4. Deploy pro-entitlement and pro-rtdn functions (`supabase functions deploy pro-entitlement` and `supabase functions deploy pro-rtdn`; both share `_shared/`). Optional secret FOUNDER_AUTO_CLAIM=off disables automatic founder grants (the code box keeps working). Supabase config.toml intentionally disables gateway JWT verification because pro-entitlement validates Supabase Auth tokens through GoTrue and pro-rtdn validates Google-issued OIDC tokens.
5. Set up Google Cloud Pub/Sub topic for Play Real-time Developer Notifications, grant publishing access to google-play-developer-notifications@system.gserviceaccount.com, and connect topic in Play Console. Make authenticated push subscription to https://PROJECT_REF.supabase.co/functions/v1/pro-rtdn. Configure GOOGLE_PUBSUB_PUSH_EMAIL as exact push service-account email, GOOGLE_PUBSUB_AUDIENCE as exact audience. Send test notification.
6. Verify GitHub Actions public variables VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY target the same Supabase project; never bundle service-role and Google private keys. Monitor failed verification and Pub/Sub dead letters.

## Founding testers: grandfather migration and trust tradeoff
- Founders never lose Pro on update: the app ORs the on-device install-date unlock with server status, so nothing depends on the server for them. The server grant exists so founders keep Pro after a reinstall on the same phone and so later server-only decisions have a record.
- Trust: `firstInstallTime` is self-reported. Anyone who modifies the app or calls the endpoint with a forged time before the cutoff gets a founder grant. That is the same trust level as the on-device unlock (a modified APK can already unlock itself), it unlocks no money and no other user's data, and the window is fixed in SQL (2026-10-01 to the cutoff). Mitigations: FOUNDER_AUTO_CLAIM=off closes the endpoint; `pro_founders.source`/`first_install_at` let you audit and revoke `install_date` grants. TODO: require a Play Integrity verdict (MEETS_DEVICE_INTEGRITY, PLAY_RECOGNIZED) in claimFounderInstall once the Integrity API is enabled.
- Recovery on a NEW phone (different ANDROID_ID) still needs a one-time code: generate 24+ random characters, store only SHA-256 in pro_founder_codes, send privately. Factory reset also changes ANDROID_ID.
- Before release: confirm on a founder phone that Pro stays on offline, `founder-install` returns foundingTester true, and a row appears in pro_founders.

## Limitations and security
- A copied genuine Play purchase token cannot move a purchase to another account unless the thief also presents the victim phone's account hash (SHA-256 of an app-scoped ANDROID_ID only readable by Patrol Radar on that phone). Purchases made on a different phone, or before setObfuscatedAccountId shipped, cannot be relinked automatically: use support with the Google Play order number.
- The device caches the last verified status (`pr.pro.verified`) so paying users keep Pro offline; a server "not Pro" answer clears it. The server honors rows verified in the last 3 days (was 30 minutes) when Google is unreachable; RTDN revocations still remove access immediately.
- A purchase token is not a purchase until server-validated. Refund/revocation and expired subscriptions remove access. A paid cancellation typically keeps access until verified expiry.
- The heatmap source files under public/data/stop-heat are publicly downloadable; this gate protects in-app enhanced features, not confidential data files. Do not market them as exclusive secret datasets.
- Never ship Pro checkout with unavailable backend or unprovisioned founding grants. Never publish to production.
